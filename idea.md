點子總覽
pytest-synapse is a Python SDK and pytest plugin designed to provide deep API contract test coverage by bridging dynamic test execution with static OpenAPI definitions. Its core innovation, the Synapse Interceptor, transparently captures decrypted HTTP traffic (requests and responses) by intelligently monkey-patching common Python HTTP clients like requests and httpx at a high level. This non-intrusive approach eliminates the need for complex proxy setups or test code modifications, enabling pytest-synapse to generate granular coverage reports on OpenAPI paths, methods, request bodies, response statuses, and schemas, all seamlessly integrated into standard pytest workflows with minimal configuration.

pytest-synapse for OpenAPI Test Coverage
The solution proposed is pytest-synapse, an MVP Python SDK and pytest plugin that establishes a robust bridge between dynamic test execution and static OpenAPI definitions. Its core innovation is the Synapse Interceptor, a framework designed to overcome the historical challenges of transparent, adaptive, and deep-level HTTP traffic interception in Python test environments.

The Synapse Interceptor
The fundamental challenge in API contract coverage is acquiring the actual HTTP traffic (requests and responses) generated by tests in a non-intrusive manner. Traditional approaches involving proxies or custom HTTP client libraries force developers into complex setups or rewrite their test code. The Synapse Interceptor breaks this cycle by employing targeted, high-level monkey-patches on the most common Python HTTP client libraries (e.g., requests, httpx, urllib3). This strategy ensures:

Transparency: Tests written using standard requests.get(), httpx.post(), or similar calls require no modifications. The interception happens behind the scenes.
HTTPS Compatibility: By patching above the Transport Layer Security (TLS) layer—for instance, at the requests.Session.send or httpx.BaseTransport.handle_request level—the interceptor accesses already decrypted request and response payloads. This inherently resolves the complexities and security concerns associated with Man-in-the-Middle (MITM) proxies and certificate management for HTTPS.
Adaptive Client Support: Instead of a single, brittle patch, Synapse Interceptor intelligently detects and applies the appropriate interception strategy based on the HTTP client libraries present and used during the test run. This makes it resilient and compatible with diverse test environments.
Normalized Data Flow: Regardless of the originating HTTP client, all captured traffic is converted into a consistent internal data model (CapturedTrafficEvent). This uniformity simplifies subsequent coverage calculation and reporting.
This adaptive, transparent, and high-fidelity interception is a key enabler for pytest-synapse to provide seamless and deep OpenAPI coverage reporting in Python.

Main Components of pytest-synapse (SDK Interface and Pytest Integration)
pytest-synapse is structured around several core components that collectively provide its functionality as a Python SDK, with pytest integration forming a fundamental part of its operation.

Synapse Interceptor (Core Interception Component):

Role: The engine responsible for transparently capturing HTTP requests and responses made by test code. This is where pytest-synapse fulfills the requirement to "capture actual network requests/responses."
Mechanism: Activated during the pytest_sessionstart hook, it dynamically iterates through a registry of InterceptionStrategies. For popular libraries like requests, it replaces methods like requests.Session.send with a wrapper. This wrapper intercepts the PreparedRequest and Response objects (already parsed and decrypted by the underlying library), converts them into synapse_types.CapturedTrafficEvent objects, and then calls the original method to allow the network request to proceed. Similar strategies apply to httpx by patching httpx.BaseTransport methods (e.g., handle_request). This intelligent patching ensures broad compatibility and non-invasiveness.
SynapseFlowLogger:

Role: Acts as a thread-safe, process-aware ephemeral storage for all CapturedTrafficEvent objects during a pytest session. This ensures that all traffic, regardless of which test function generated it, is collected.
Implementation: Utilizes a pytest fixture (synapse_flow_log) which automatically accumulates CapturedTrafficEvent objects throughout the test run. Each event contains:
test_id: The pytest node ID to link traffic back to its originating test.
request: A normalized synapse_types.HttpRequest (method, URL path, query parameters, headers, body).
response: A normalized synapse_types.HttpResponse (status code, headers, body).
timestamp: The time of the event.
OpenAPISpecParser:

Role: This SDK component loads, parses, and resolves an OpenAPI specification from a YAML or JSON file, creating an optimized internal representation that the SynapseCoverageEngine can easily traverse.
Implementation: It leverages external robust libraries like openapi-core for parsing and schema resolution, ensuring correctness and adherence to the OpenAPI standard. The output is a synapse_spec.OpenAPIDocumentModel object, representing the OpenAPI document hierarchically with PathItem, Operation, RequestSchema, and ResponseSchema entities.
SynapseCoverageEngine (Coverage Calculator & Core Mapping Logic):

Role: The analytical heart of pytest-synapse. It compares the aggregated CapturedTrafficEvent data from the SynapseFlowLogger against the OpenAPIDocumentModel generated by the OpenAPISpecParser to determine coverage for OpenAPI paths, HTTP methods, request bodies, response schemas, and status codes.

Process:

Path/Method Matching: For each HttpRequest, the engine uses a sophisticated routing algorithm (e.g., werkzeug.routing.Map) built from the OpenAPIDocumentModel.paths. This allows it to correctly match dynamic URL paths like /users/123 to templated paths like /users/{id} and identify the corresponding Operation (e.g., GET for /users/{id}). Upon a successful match, the relevant path and method within its internal CoverageMap are marked COVERED.
Request Body Coverage: If the matched Operation defines a requestBody schema and the HttpRequest contains a body, openapi_core.validation.request.validate_request is called. A successful validation marks the specific requestBody schema within the CoverageMap as COVERED, implying that the test has provided a valid request body for that operation.
Response Status Code Coverage: For the HttpResponse corresponding to the matched request, the engine checks if its status_code is defined in the Operation.responses section of the OpenAPI spec. If found, this specific status code entry is marked COVERED.
Response Body Coverage: If the Operation.responses for the given status_code defines a schema, openapi_core.validation.response.validate_response is used to validate the HttpResponse.body. Successful validation marks that specific response schema as COVERED.
Coverage Data Structure: The engine populates a synapse_report.CoverageMap object. This map mirrors the OpenAPIDocumentModel structure but augments it with coverage status flags (COVERED, UNCOVERED, PARTIALLY_COVERED, NOT_APPLICABLE) for each relevant element.

ReportRenderer:

Role: The final SDK component responsible for transforming the OpenAPICoverageReport (the CoverageMap) into user-friendly and actionable output.
Output Types: For the MVP, it focuses on:
CLI Summary: A concise overview of total vs. covered paths, methods, request bodies, and response schemas.
Detailed CLI Output: A more granular, tree-like structure displaying each path, method, status code, and schema element with its coverage status.
JSON Report: A machine-readable JSON representation of the CoverageMap, suitable for integration with other tools or CI/CD pipelines.
Typical User Workflow for Integrating and Using the Tool
pytest-synapse prioritizes ease of installation and configuration, allowing users to leverage their existing pytest test suites with minimal overhead.

Installation (easy to install and configure):
Users install the SDK via pip:

pip install pytest-synapse openapi-core
(Explicitly including openapi-core clarifies a core dependency that may have specific validation needs).

Configuration (pytest.ini):
The plugin is enabled and configured via pytest.ini. This configuration step defines the OpenAPI specification to be used and the desired output format for the coverage report.

# pytest.ini
[pytest]
addopts = --openapi-spec=./openapi.yaml --synapse-report=coverage.json --synapse-report-format=json
# Optional settings could include:
# --synapse-ignore-paths=/health,/metrics # To exclude specific paths from coverage calculation
# --synapse-report-format=cli_detailed    # For verbose console output
This automatically registers pytest-synapse as a plugin for the pytest run.

Test Writing (Leveraging existing tests):
Crucially, users write their API integration tests as they normally would, utilizing their preferred Python HTTP client (e.g., requests, httpx). No modifications to the API client instantiation or method calls are required thanks to the Synapse Interceptor.

# tests/test_my_api.py
import requests

BASE_URL = "http://localhost:8000"

def test_get_user_by_id_200():
    response = requests.get(f"{BASE_URL}/users/1")
    assert response.status_code == 200
    assert "id" in response.json() and "name" in response.json()

def test_create_user_201():
    user_data = {"name": "Alice", "email": "alice@example.com"}
    response = requests.post(f"{BASE_URL}/users", json=user_data)
    assert response.status_code == 201
    assert response.json()["id"] is not None

def test_update_user_400_invalid_email():
    # This test might intentionally trigger a 400 bad request as defined in the spec
    response = requests.put(f"{BASE_URL}/users/1", json={"email": "invalid"})
    assert response.status_code == 400
    assert "error_message" in response.json() # Assuming spec defines this
Running Tests (capture actual network requests/responses):

pytest
During this standard pytest execution, pytest-synapse's Synapse Interceptor silently intercepts all HTTP traffic, logs it via SynapseFlowLogger, and upon pytest_sessionfinish, the SynapseCoverageEngine processes this data against the openapi.yaml to generate the specified report.

Core Logic for Identifying and Mapping Executed API Calls
The SynapseCoverageEngine operates on a meticulously designed logic to identify and map executed API calls (CapturedTrafficEvent objects) to the definitions in the OpenAPIDocumentModel.

Request Matching (synapse_engine.match_request_to_operation):

For each HttpRequest received from the SynapseFlowLogger, the engine first normalizes the URL path (removing query parameters).
It then utilizes a routing library (like werkzeug.routing.Map) constructed from the OpenAPIDocumentModel.paths keys (which are typically templated paths like /users/{userId}). This efficiently matches concrete paths (e.g., /users/123) to their templated counterparts.
Once a path match is found, it verifies if the HttpRequest.method (e.g., GET, POST) exists within the PathItem definition in the OpenAPI spec.
A successful match identifies the specific OpenAPIDocumentModel.Operation that corresponds to the executed request.
Granular Coverage Marking:
Upon successfully identifying an Operation, SynapseCoverageEngine updates the CoverageMap at various levels:

Path/Method Coverage: The entry for the matched path and method in the CoverageMap is marked as COVERED.
Request Body Coverage:
If the identified Operation includes a requestBody definition in the OpenAPI spec, and the HttpRequest actually contained a body, openapi_core.validation.request.validate_request() is invoked using the HttpRequest.body and the operation's request body schema.
If this validation is successful, the request_body component of the CoverageMap for that Operation is marked COVERED. This means the test successfully sent data conforming to the documented request schema.
Response Status Code Coverage:
The HttpResponse.status_code from the captured event is checked against the responses defined in the Operation within the OpenAPI spec.
If a matching status_code entry is found, that specific status_code within the CoverageMap for the Operation is marked COVERED.
Response Body Schema Coverage:
If a schema is defined for the matched status_code in the Operation.responses, openapi_core.validation.response.validate_response() is executed with the HttpResponse.body and the response schema definition.
Upon successful validation, the response_schema component for that status_code within the CoverageMap is marked COVERED, indicating that the test received a response body conforming to the documented schema.
This detailed, step-by-step validation against the OpenAPI specification provides the granular definition of 'coverage' required for an actionable report.

MVP Scope and Future Enhancements
The MVP (Minimum Viable Product) focuses on delivering core, indispensable functionality while maintaining a clear path for future growth.

MVP Scope (prioritize core functionality):

Python Language Support: Strictly designed and implemented in Python.
SDK Interface: Programmatic access to SynapseCoverageEngine and OpenAPISpecParser components for advanced integration.
pytest Integration: Full utilization of pytest plugin hooks for seamless setup, teardown, data collection, and reporting.
Interception: Robust and transparent interception for requests and httpx (sync mode) using the Synapse Interceptor.
Coverage Definition: Calculates coverage for:
OpenAPI Paths (e.g., /users/{id}).
HTTP Methods (GET, POST, PUT, DELETE).
Presence and schema validity of Request Bodies.
Presence of Response Status Codes in the spec.
Presence and schema validity of Response Schemas for each status code.
Report: Generates a clear CLI summary and a detailed, machine-readable JSON report showing covered/uncovered status at various granular levels.
Ease of Use: Simple installation via pip and configuration through pytest.ini.
Network Capture: The Synapse Interceptor captures actual network requests and responses as initiated by tests.
Future Enhancements:

Deeper Schema Coverage: Implement tracking for individual schema properties/fields, including support for oneOf/anyOf/allOf and enum values, to report if specific data structures or enum choices were exercised.
httpx Async Support: Extend Synapse Interceptor to handle asynchronous httpx calls transparently.
Expanded Client Support: Add InterceptionStrategy implementations for other popular Python HTTP clients like aiohttp and urllib.request.
HTML/Interactive Reports: Develop visual, interactive dashboards for coverage, potentially showing discrepancies or coverage over time.
Exclusion Rules: More sophisticated configuration options to ignore specific paths, methods, or status codes based on regex or glob patterns.
Performance Metrics: Integrate basic performance data (e.g., request latency) into the coverage reports.
Contract Violation Detection: Beyond coverage, actively report instances where actual traffic violates the OpenAPI specification (e.g., unexpected fields in a response, incorrect data types). This would leverage openapi-core's validation error reporting.
OpenAPI Evolution: Features for comparing coverage across different versions of an OpenAPI specification.

import requests

BASE_URL = "http://localhost:8000"

def test_get_existing_user():
    # Test 1: Happy path, user exists
    response = requests.get(f"{BASE_URL}/users/123")
    assert response.status_code == 200
    assert response.json() == {"id": 123, "name": "Alice", "email": "alice@example.com"}

def test_get_non_existing_user():
    # Test 2: User not found path, as per spec
    response = requests.get(f"{BASE_URL}/users/999")
    assert response.status_code == 404
    assert response.json() == {"message": "User 999 not found"}
